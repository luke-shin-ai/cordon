Build a Guarded Device Node on QNX 8.0 and Verify It Under QEMU

Overview

Estimated time: 3:00

In this codelab you build a small but complete QNX 8.0 service that owns one path in the pathname space, /dev/cordon. Four things are wired together:

  • a resource manager that answers a status read and records write events
  • a security policy that decides which process may read and which may write
  • a supervisor that starts the service again after it dies
  • a boot image plus a host gate that turns the run into PASS or FAIL

The point is not the service itself. The point is the last step: an image is released only when every check the verifier expects has a recorded verdict. Nothing in this codelab measures time, rate or resource use. Every decision is a true or false question: did the answer arrive, which errno came back, did the sequence number change.

Build and Boot a QNX 8.0 Image

Estimated time: 8:00

mkqnximage is part of the SDP and builds a bootable QEMU image from your own file list. Make a project directory and build the stock image once, before adding anything of your own, so you know the base is good.

mkdir -p ~/cordon-lab && cd ~/cordon-lab
mkqnximage --type=qemu --arch=x86_64 --build_dir=$PWD/base

The build writes ifs.bin and disk-qemu next to a build directory. Boot it with the IFS passed as the kernel:

qemu-system-x86_64 -cpu max -m 384 -snapshot -nographic \
  -drive file=$PWD/base/disk-qemu,format=raw,if=ide \
  -kernel $PWD/base/ifs.bin

Two details matter on QEMU. Without -cpu max the QNX kernel may stop early on a CPUID check and print nothing. The image is a multiboot IFS, so pass it with -kernel and also attach the disk.

You are in when the console prints a QNX banner and Startup complete, and the guest shell answers:

uname -a

Keep this shell open. Every command in the next steps runs either on this guest or on the host beside it.

Write the Resource Manager

Estimated time: 12:00

A QNX resource manager registers a path, then receives messages for it. The kernel routes a client's open, read and write to your handlers. Save this as cordon.c on the host.

#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/dispatch.h>
#include <sys/iofunc.h>
#include <sys/resmgr.h>
#include <sys/slog2.h>

static iofunc_attr_t attr;
static int events;
static char status[256];

/* One line per fact. The host decides what the line means. */
static void emit(const char *kind, const char *detail)
{
    printf("CORDON-OBS service=%s %s\n", kind, detail);
    fflush(stdout);
}

static int cordon_read(resmgr_context_t *ctp, io_read_t *msg, RESMGR_OCB_T *ocb)
{
    iofunc_ocb_t *o = (iofunc_ocb_t *)ocb;
    int n;

    if (iofunc_read_verify(ctp, msg, ocb, NULL) != EOK) {
        return EACCES;
    }
    n = snprintf(status, sizeof status, "pid=%d events=%d\n", (int)getpid(), events);
    if (o->offset >= n) {
        _IO_SET_READ_NBYTES(ctp, 0);
        return _RESMGR_NPARTS(0);
    }
    SETIOV(ctp->iov, status + o->offset, n - o->offset);
    _IO_SET_READ_NBYTES(ctp, n - o->offset);
    o->offset = n;
    return _RESMGR_NPARTS(1);
}

static int cordon_write(resmgr_context_t *ctp, io_write_t *msg, RESMGR_OCB_T *ocb)
{
    char record[128];
    int n = msg->i.nbytes;

    if (iofunc_write_verify(ctp, msg, ocb, NULL) != EOK) {
        return EACCES;
    }
    if (n <= 0 || n >= (int)sizeof record) {
        return EINVAL;
    }
    if (resmgr_msgread(ctp, record, n, sizeof msg->i) != n) {
        return EFAULT;
    }
    record[n] = '\0';
    events++;
    emit("accept", record);
    _IO_SET_WRITE_NBYTES(ctp, msg->i.nbytes);
    return _RESMGR_NPARTS(0);
}

int main(void)
{
    dispatch_t *dpp;
    resmgr_attr_t rattr;
    resmgr_connect_funcs_t connect;
    resmgr_io_funcs_t io;
    dispatch_context_t *ctp;

    dpp = dispatch_create();
    memset(&rattr, 0, sizeof rattr);
    rattr.nparts_max = 1;
    rattr.msg_max_size = 2048;
    iofunc_func_init(_RESMGR_CONNECT_NFUNCS, &connect, _RESMGR_IO_NFUNCS, &io);
    iofunc_attr_init(&attr, S_IFCHR | 0666, NULL, NULL);
    io.read = cordon_read;
    io.write = cordon_write;

    if (resmgr_attach(dpp, &rattr, "/dev/cordon", _FTYPE_ANY, 0,
                      &connect, &io, &attr) == -1) {
        perror("resmgr_attach");
        return 1;
    }
    emit("up", "path=/dev/cordon");

    ctp = dispatch_context_alloc(dpp);
    for (;;) {
        ctp = dispatch_block(ctp);
        if (ctp == NULL) {
            break;
        }
        dispatch_handler(ctp);
    }
    return 0;
}

Build it for the target and copy it into the image directory you will grow in a later step:

qcc -Wall -Wextra -O1 -o build/cordon cordon.c

resmgr_attach is the call that makes /dev/cordon appear. iofunc_read_verify and iofunc_write_verify apply the default permission model; the policy step replaces that default with an explicit question to secpol.

Run it on the guest for now:

/proc/boot/cordon &
ls -l /dev/cordon

Talk to the Node From a Client

Estimated time: 6:00

A tiny client makes the two operations visible. Save it as client.c.

#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    char buf[256];
    int fd, n;

    if (argc < 2) {
        return 2;
    }
    if (strcmp(argv[1], "status") == 0) {
        fd = open("/dev/cordon", O_RDONLY);
        if (fd < 0) {
            printf("CORDON-OBS client op=status result=ERR errno=%d\n", errno);
            return 1;
        }
        n = read(fd, buf, sizeof buf - 1);
        if (n < 0) {
            printf("CORDON-OBS client op=status result=ERR errno=%d\n", errno);
            return 1;
        }
        buf[n] = '\0';
        printf("CORDON-OBS client op=status result=OK status=%s", buf);
        close(fd);
        return 0;
    }
    if (strcmp(argv[1], "write") == 0) {
        fd = open("/dev/cordon", O_WRONLY);
        if (fd < 0) {
            printf("CORDON-OBS client op=open result=ERR errno=%d\n", errno);
            return 1;
        }
        if (write(fd, "zone=main", 9) < 0) {
            printf("CORDON-OBS client op=write result=ERR errno=%d\n", errno);
            return 1;
        }
        printf("CORDON-OBS client op=write result=OK\n");
        close(fd);
        return 0;
    }
    return 2;
}

Build and try both operations:

qcc -Wall -Wextra -O1 -o build/cordon-client client.c
./build/cordon-client status
./build/cordon-client write

The status read returns the service pid and the event count. The write adds one event. Nothing has been secured yet: any process that can open the path can write to it. That is what the next step changes.

Add a Security Policy

Estimated time: 12:00

secpol decides access in the kernel and in the service. A policy file names types, custom permission classes and the rules between them. Save this as cordon.policy.

type cordon_t;
type cordon_writer_t;
type cordon_probe_t;

class cordon { write status };

allow_attach cordon_t /dev/cordon;
allow cordon_t self:ability { spawn };
allow { cordon_writer_t cordon_probe_t } cordon_t : channel connect;
allow { cordon_writer_t cordon_probe_t } cordon_t : cordon status;
allow cordon_writer_t cordon_t : cordon write;

Three layers are in play:

  1. allow_attach decides which process may put a channel at the path.

with no rule is refused by the kernel before your code runs.

  1. channel connect decides which type may reach the service at all. A type

The service asks the policy on every read and write instead of trusting itself.

  1. The custom class cordon decides the two operations your handlers perform.

Compile and push the policy, then start the service and the clients with an explicit type:

secpolcompile -o secpol.bin cordon.policy
secpolpush
secpol -Q
on -T cordon_t ./build/cordon &
on -T cordon_probe_t ./build/cordon-client write
on -T cordon_writer_t ./build/cordon-client write

The probe is refused and the writer succeeds. A refusal from the policy check inside the service comes back as errno=13 (EACCES). A client type with no connect rule never reaches the service and gets errno=1 (EPERM) from the kernel.

Two details cost time if you miss them:

written against cordon_t, so the service must resolve that name at startup and pass the number, not 0, to secpol_check_permission. Passing 0 matches nothing and denies every request.

  • secpol_get_type_id() returns the number your own channel carries. Rules are

with secpol_transition_type(). A process started with on -T reports 0. The type the service sees arrives in the message it received, so log that.

  • secpol_type_id() in a client is only accurate for processes that change type

To make the service consult the policy, add the check to both handlers:

static secpol_permission_t *perm_write;
static uint32_t object_type;

/* in main, after secpol_open(NULL, SECPOL_USE_AS_DEFAULT) */
object_type = secpol_get_type_id(NULL, "cordon_t");
perm_write = secpol_get_permission(NULL, "cordon", "write", 0);

/* in cordon_write, before reading the message */
if (perm_write == NULL ||
    secpol_check_permission(&ctp->info, object_type, perm_write) != 0) {
    emit("deny", "kind=write result=DENY check=EPERM");
    return EACCES;
}

Survive a Process Death

Estimated time: 10:00

A service that dies takes its path with it. On QNX the High Availability Manager can restart a process, but it is an optional package that a base SDP install does not include. The primitives it drives are in libc, so a supervisor is short: posix_spawn, waitpid, and a sequence number that the service reads at startup.

#include <spawn.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

extern char **environ;

int main(int argc, char **argv)
{
    int seq = 0, max = 4;

    while (seq < max) {
        pid_t pid;
        int status = 0;
        int signal = 0;
        char number[16];
        char *args[] = { argv[1], "-r", number, NULL };

        seq++;
        snprintf(number, sizeof number, "%d", seq);
        if (posix_spawn(&pid, argv[1], NULL, NULL, args, environ) != 0) {
            printf("CORDON-OBS supervise spawn=ERR seq=%d\n", seq);
            return 1;
        }
        printf("CORDON-OBS supervise spawn seq=%d pid=%d\n", seq, (int)pid);
        fflush(stdout);
        waitpid(pid, &status, 0);
        if (WIFSIGNALED(status)) {
            signal = WTERMSIG(status);
        }
        printf("CORDON-OBS supervise exit seq=%d signal=%d\n", seq, signal);
        fflush(stdout);
        printf("CORDON-OBS supervise respawn next_seq=%d\n", seq + 1);
        fflush(stdout);
    }
    return 0;
}

Start the service through the supervisor and kill the child from another shell. The console shows the exit, the respawn and a new service start with the next sequence number. The service prints its sequence in the status read, so a client can tell the difference between the service that died and the one that replaced it.

on -T cordon_t ./build/cordon-supervise ./build/cordon &
sleep 1
kill -9 $(pidin -F "%N %p" | awk '/cordon$/ {print $2}')
./build/cordon-client status

Put It in the Boot Image

Estimated time: 10:00

Now move the pieces into the image so a boot produces the whole run. Add a startup snippet that pushes the policy, starts the supervisor, waits for the path, and runs the clients in a fixed order.

secpolpush
on -T cordon_t /proc/boot/cordon-supervise /proc/boot/cordon &
while [ ! -e /dev/cordon ]; do sleep 1; done
on -T cordon_probe_t /proc/boot/cordon-client write
on -T cordon_writer_t /proc/boot/cordon-client write
echo CORDON-G2-COMPLETE

Build two images from the same sources. The only difference is the order: in the second one the first client runs before the service exists.

mkqnximage --type=qemu --arch=x86_64 --build_dir=$PWD/normal   --post_startup=normal.sh
mkqnximage --type=qemu --arch=x86_64 --build_dir=$PWD/broken   --post_startup=broken.sh

Both images boot. In the broken image the first client fails with errno=2 (ENOENT) because /dev/cordon is not there yet, and the same client succeeds after the service starts. That failure is the evidence that the order matters. An image that starts the service first must never show it.

Judge the Image From the Host

Estimated time: 6:00

The target prints facts. The host decides. A gate reads the observations from a serial console, applies a rule per scenario, and returns one exit code. The companion repository for this codelab carries such a gate; clone it beside your lab and point it at the two logs:

git clone https://github.com/luke-shin-ai/cordon.git
host/cordon run --console-normal normal-console.log \
  --console-negative broken-console.log --out run --gate
host/cordon bundle run bundle

cordon gate exits 0 only when every scenario matched its expectation, including the negative control, which must FAIL. Anything else exits 1 and names the scenario that disagreed.

The last piece is the release note. A draft can come from a template or from a language model; both go through the same verifier, which checks every sentence against the bundle and deletes the ones the evidence does not support:

host/cordon note bundle --out note

A sentence that names a scenario the run did not produce, quotes a hash that is not in the image record, or reports a pass where the bundle recorded a fail is removed and listed in dropped.md. A sentence that states a performance result rejects the whole note, because the non-commercial license restricts publishing evaluation results.

Clean Up

Estimated time: 2:00

Stop the supervisor and the service, and remove the lab images when you are done:

kill $(pidin -F "%N %p" | awk '/cordon/ {print $2}')
rm -rf ~/cordon-lab

If you pushed a policy and want the system back to its default behaviour, reboot the guest. The policy lives in the kernel until the next boot.
